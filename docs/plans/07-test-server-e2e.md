# Plan 07: The test server as the repo's standard for end-to-end checks

Goal: every feature that touches the Jellyfin API or the player is verified against the local
test server (`scripts/test-server/`) built in plan 06, using generated media with known contents,
and the checks that can be automated run from one Gradle task. New features add their fixtures to the
server instead of improvising them.

**Status (2026-10-20):** queued, nothing built. Not started until plan 06 (Phase 3) is done. Written
without a full design interview: every call marked *(my call)* is a guess for the owner to confirm.

## Why

- Plan 03 found bugs only a real server showed (the server ignoring track indices without a media
  source id, defaults dropped by `Json`). MockEngine tests can't catch that class of bug.
- The generated media ("dummy stream": ffmpeg `testsrc2` video, sine audio, known chapters) is
  deterministic: timestamps are known to the second, so a test can assert exact behaviour. It needs no
  licensed media, and anyone can rebuild it from the repo.
- Today it is used by hand. The roadmap's cross-cutting "Testing" item already asks for contract tests
  against the Jellyfin API.

## Decisions

- **Three levels, built in this order *(my call)*:** a convention (docs and `CLAUDE.md`), automated
  contract tests in `shared/`, and UI end-to-end later. Level 3 needs a new framework (Compose UI tests,
  XCUITest) and is out of scope until the owner approves it.
- **E2E tests are opt-in.** `./gradlew :shared:allTests` stays hermetic and runs without podman. The
  e2e set runs only when `VIBEYFIN_E2E_URL` (and credentials) are set, through its own task
  (`:shared:e2eTest`, name *(my call)*). They use the app's own repositories, not hand-built requests.
- **Fixtures are code.** Each fixture is generated by `make-media.sh`, listed in the catalogue in
  `docs/test-server.md` (what it is, which feature needs it), and referenced by name from tests.
  Fixture names are stable; changing one is a reviewed change.
- **Failure fixtures and server behaviours are first-class**, because real media rarely gives them:
  no segments, no trickplay, a file AVPlayer can't open (MKV), DTS audio, text and image subtitles, a
  truncated file; and behaviours: a 401 on the stream only, a dropped connection, a slow response
  (a small proxy in front of the server, scripted).
- **Plan 06's deferred items from the test server** are handled here: write the media to a temp name then
  move it, build the auth header once, drop the no-op `|| true`.

## Phase A: Convention and catalogue

- `docs/test-server.md` gains a fixture catalogue and a "how to add a fixture" section.
- `CLAUDE.md` gets a short "Test server" section: a feature that touches the API or playback is
  verified against it, and a new feature adds its fixtures. (Owner approves the CLAUDE.md edit.)
- Done when: the catalogue lists every fixture `make-media.sh` creates, and the working agreement names
  the server as part of "done".

## Phase B: Failure fixtures

- Generate the failure cases above, each documented with the behaviour it should produce in the app.
- Done when: `start.sh` produces them from scratch and a script lists them with their expected
  Jellyfin item properties.

## Phase C: Server behaviour switches

- A scripted proxy in front of the server with named modes (`ok`, `stream-401`, `drop`, `slow`),
  switched by a command, replacing the by-hand proxy of plan 03.
- Done when: each mode can be set and cleared in one command and its effect is shown with `curl`.

## Phase D: Contract tests (`:shared:e2eTest`)

- A source set or test tag in `shared/` that wires the real repositories to the server named by the
  environment, signs in, and runs: negotiation (direct, stream, transcode, no compatible stream),
  segments, trickplay, the beacon lifecycle (`Start`, `Progress`, `Stopped` reach the server), and item
  format fields.
- Done when: the task passes against a fresh `start.sh` server and is skipped, not failed, without the
  environment variables.

## Risks

- The server image and plugin versions drift. The image tag is pinned; the plugin is installed by
  version in `start.sh`.
- Trickplay and segment generation are asynchronous, so tests must poll with a bound.
- A CI that has no podman can't run level 2; it stays a local check until one does.

## Questions for the owner

1. Is `:shared:e2eTest` gated by environment variables the right shape, or should it be a Gradle
   property?
2. Is a scripted proxy for failure modes acceptable as a repo tool, or should those stay manual?
3. Should level 3 (UI end-to-end) get its own plan now, or wait?
